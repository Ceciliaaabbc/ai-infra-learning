# 实验结果：RTX 4090

**在 RTX 4090 上，GPT-2（124M）的训练吞吐从 23,653 提升到 119,443 tokens/s（5.05 倍），MFU 从 12.3% 提升到 61.9%。batch 不变时，峰值显存从 9.03 GB 降到 4.17 GB（减少 54%）。**

## 实验环境

| 项目 | 配置 |
|---|---|
| 显卡 | NVIDIA GeForce RTX 4090（24GB，sm89），AutoDL 租用 |
| 软件 | PyTorch 2.8.0 + CUDA 12.8，Python 3.12 |
| 模型 | GPT-2 124M，序列长度 T = 1024 |
| 数据 | tiny shakespeare |
| 测量方式 | 每个实验跑 50 步，前 10 步（编译、预热）不计入统计；随机种子固定为 1337 |
| 日期 | 2026-10-05 |

`check_gpu.py` 实测的 8192×8192 矩阵乘法算力：

| 精度 | 实测 | 说明 |
|---|---:|---|
| fp32（关闭 TF32） | 51.5 TFLOPS | 普通 CUDA 核心只跑到了理论峰值 82.6 的 62% |
| fp32（开启 TF32） | 84.1 TFLOPS | 走 Tensor Core，比关闭时快 1.63 倍 |
| bf16 | 153.7 TFLOPS | 达到理论峰值 165 的 93% |

## 核心发现：baseline 的瓶颈是显存读写，不是计算

TF32 能让矩阵乘法快 1.63 倍，但整体训练只快了 1.18 倍。用 Amdahl 定律反推，矩阵乘法只占每一步时间的约 **40%**：

```
1 / ((1 − f) + f / 1.63) = 1.18   →   f ≈ 0.40
```

剩下约 60% 的时间花在 softmax、LayerNorm、GELU、加法等操作上。它们计算量很小，但每个都要把整块数据从显存读出来再写回去，瓶颈在显存带宽。

所以提升最大的两项是 **compile（×1.83）** 和 **FlashAttention（×1.29）**：它们都是在减少显存读写，而不是让计算变快。

## 逐项分析

**1. TF32（×1.18）**：原因见上面的 Amdahl 分析。显存不变，因为 TF32 只改变矩阵乘法内部的计算精度，数据仍以 fp32 存储。

**2. bf16（×1.28）**：速度提升符合预期，但显存只少了 0.4 GB。autocast 会让 softmax 和 cross_entropy 保持 fp32 计算，而这两处恰好是最大的张量：attention 的 (B, 12, T, T) 分数矩阵经过 softmax 后仍是 fp32，后面的矩阵乘法还要再存一份 bf16 副本；输出层 (4096, 50257) 的 logits 在算 loss 时也会转成 fp32。**混合精度不等于显存减半。**

**3. torch.compile（×1.83，单项提升最大）**：把那 60% 读写密集的小操作融合成少数几个 kernel，大幅减少显存读写。显存也少了 2.2 GB：融合后很多中间结果不再单独保存，一些计算量小的操作在反向时直接重算。第 0 步用了 23 秒，这是编译时间。

**4. FlashAttention（×1.29，显存再降 2.3 GB）**：不再把 T×T 的分数矩阵写进显存，同时节省了显存容量和读写时间。验证了“attention 分数矩阵是显存大户”的预测。

**5. 词表补齐到 50304（×0.99，没有效果）**：Karpathy 在 A100 上测到约 4% 的提升，这里测不出差别。在 4090 加上这个版本的 cuBLAS 和 compile 下，50257 这种不规整的尺寸已经处理得足够高效。**同一个技巧换了硬件或软件版本就可能失效，必须实测。**

**6. fused AdamW（×1.15）**：每步从 48.8 ms 降到 42.3 ms，省了 6.5 ms。粗略估算：foreach 版本分约 8 次遍历参数相关的数据，共读写约 10 GB；fused 版本一次完成，只读写约 3.5 GB。按 4090 约 1 TB/s 的显存带宽算，能省约 6 ms，和实测吻合。优化器耗时和 batch 大小无关，B=4 时每步本身很短，所以它的占比较大。

**7. batch 从 4 加到 16（×1.23）**：token 数变成 4 倍，每步时间只增加到 3.26 倍。矩阵更大，GPU 吃得更饱；优化器等固定开销也被分摊了。激活显存基本随 batch 线性增长：B=4 时约 2.3 GB，B=16 时约 9.6 GB。

**8–10. activation checkpointing：用速度换显存**

| | B=16 | B=32 |
|---|---|---|
| 不开 checkpointing | **119,443**，11.47 GB | **OOM** |
| 开 checkpointing | 104,957，6.75 GB | 110,340，11.94 GB |

- **代价**：慢了 14%。理论上要重算每个 Block 的前向，FLOPs 约增加 24%（输出层不在 Block 里，不用重算），实测代价比理论值小。
- **收益**：激活显存减少 49%，B=32 也能跑了。
- **但最快的仍是实验 7**：batch 加大带来的 +5% 抵不过重算的 −14%。checkpointing 真正的用武之地是“不开就跑不起来”的场景，比如超长序列。
- **MFU 和 HFU**：实验 8 的 MFU 是 54.4%，因为 MFU 不计入重算的算力。把重算也算上的硬件利用率（HFU）约为 54.4% × 1.24 ≈ 67%。
- **实验 9 为什么第 0 步之后才 OOM**：最可能的原因是，AdamW 的 m 和 v 两份状态（共 0.93 GB）在第一次 `optimizer.step()` 时才分配。第 0 步的前向和反向时它们还不存在，从第 1 步开始一直占着显存。再加上按线性外推激活值就要约 21 GB，已经接近 23.5 GB 的上限。

## 其他观察

- **compile 会缓存编译结果**：实验 6 的第 0 步只用了 2 秒，其他开 compile 的实验要 17 到 23 秒。实验 6 和实验 5 的模型结构完全相同（只换了优化器，优化器不参与编译），直接复用了磁盘上的编译缓存。
- **优化没有影响训练结果**：B=4 的 7 组实验，最终 loss 都在 6.11 到 6.16 之间，属于 50 步训练的正常波动。从实验 5 开始走势不同，是因为词表变大后随机初始化的数值全变了。B=16、B=32 的 loss 更低，是因为每步看到的数据更多，不能和 B=4 直接比较。
- **MFU 的计算口径**：attention 部分的 FLOPs 按完整矩阵计算，没有因为 causal mask 减半（PaLM 论文的算法）。如果减半，最高的 61.9% 会变成约 58%。
